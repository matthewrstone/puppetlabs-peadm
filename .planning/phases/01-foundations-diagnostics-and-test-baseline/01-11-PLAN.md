Shell setup for every command: `export PATH="$(ruby -e 'puts Gem.user_dir')/bin:$PATH"`. Commands assume cwd is the repo root.

Design decisions (Claude's discretion for FND-02):
- Environment precedence on restore: explicit `node_group_environment` parameter > `peadm/node_group_environment.json` in the backup (written by backup.pp from now on) > `peadm::get_node_group_environment($primary_target)` (the primary's current pe.conf) > production. Older backups without the file fall through to the primary's pe.conf.
- The `--pe-environment=<env>` flag is added only when the resolved environment is not `production`, so production clusters run byte-identical commands and existing spec strings stay valid. Whether `puppet-backup create` needs an environment flag was not found in PE docs (RESEARCH Pattern 5); backup records the value instead of passing a flag.
- New parameters use `Optional[Peadm::Pe_environment]` (type from plan 01-10) and `Integer[1] $service_ready_timeout = 60` (naming from plan 01-06).
- CA backend detection: matching an uncommented `puppetlabs.services.ca.database-storage-service/` line in any of `/etc/puppetlabs/puppetserver/bootstrap.cfg`, `/etc/puppetlabs/puppetserver/services.d/*.cfg`, `/opt/puppetlabs/server/apps/puppetserver/config/services.d/*.cfg` means `database`; otherwise `filesystem` when at least one of those files exists; `unknown` when none exists. `unknown` keeps today's behaviour (no pe-ca dump/restore) but prints an out::message warning naming the paths checked. The real PE 2026.0.1 layout is confirmed on a node in plan 01-13 (RESEARCH Open Question 4, assumption A9).

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Backup tarball contents -> restore control flow | The recorded environment comes from a file inside an operator-supplied backup |

| Puppet Server config files -> CA restore decision | A wrong detection skips or forces the pe-ca database restore |
