# Codebase Concerns

**Analysis Date:** 2026-11-10

## Tech Debt

**Secret-bearing files copied to replicas and compilers with world-readable mode:**
- Issue: `peadm::util::copy_file` hard-codes `mode => '0644'` and `owner => 'root'` for every file it copies. The sources include orchestrator and console encryption/secret key stores, and those files are copied with the same mode as non-secret files.
- Files: `plans/util/copy_file.pp` (line 19), `plans/subplans/configure.pp` (lines 78-83, `replica_content_sources`), `plans/add_replica.pp` (lines ~101-112, `$content_sources`), `tasks/mkdir_p_file.sh`
- Impact: `/etc/puppetlabs/orchestration-services/conf.d/secrets/keys.json`, `/etc/puppetlabs/orchestration-services/conf.d/secrets/orchestrator-encryption-keys.json`, and `/etc/puppetlabs/console-services/conf.d/secrets/keys.json` end up readable by any local user on the replica (and the file contents also transit through Bolt task parameters and `read_file` stdout).
- Fix approach: Make the mode a per-path parameter. Use `0600` (or the mode of the source file) for everything under `secrets/`. Verify the mode on the source with `read_file`/`stat` and preserve it. Add a unit spec for `copy_file` that asserts the mode for secret paths.

**Console admin password left in `/tmp/pe.conf`:**
- Issue: The installer's `pe.conf` (generated by `peadm::generate_pe_conf`, which requires `console_admin_password`) is uploaded to `/tmp/pe.conf` via `peadm::file_content_upload` and is consumed by `puppet-enterprise-installer -c`. Nothing in the plan or `tasks/pe_install.sh` removes that file afterward.
- Files: `plans/subplans/install.pp` (lines 194-244, 364, 400, 423, 636-640), `functions/generate_pe_conf.pp`, `lib/puppet/functions/peadm/file_content_upload.rb` (uses a secure `Tempfile` locally, but the remote copy is not secured), `tasks/pe_install.sh`
- Impact: Plaintext console admin password persists in `/tmp` on every PE node after install. `/tmp` is commonly world-readable.
- Fix approach: After the installer finishes (success or failure), run `run_command('rm -f /tmp/pe.conf', ...)` on each target. Alternatively, write it to a root-only directory with `0600`.

**Hard-coded RBAC token path and default file mode:**
- Issue: `tasks/rbac_token.rb` writes the admin token to `/root/.puppetlabs/token` with `File.open(..., 'w')` and no explicit mode, so the token is created with the process umask (commonly `0644`). The path is hard-coded to `/root` and ignores the `HOME` logic used by `tasks/enable_replica.sh`, `tasks/provision_replica.sh`, and the `token_file` parameter.
- Files: `tasks/rbac_token.rb` (`execute!`), `tasks/enable_replica.sh`, `tasks/provision_replica.sh`
- Impact: A long-lived (`1y` default `token_lifetime`) admin bearer token may be readable by unprivileged local users. The token path is also inconsistent across tasks.
- Fix approach: Create the file with `File.open(path, 'w', 0o600)` and `chmod` after write, and resolve the token path the same way the shell tasks do.

**Duplicated TLS client setup across Ruby tasks:**
- Issue: About 15 files under `tasks/` each build their own `Net::HTTP` client with cert/key loading and `verify_mode` settings. There is no shared helper, so verification settings have drifted (see the TLS entry under Security).
- Files: `tasks/rbac_token.rb`, `tasks/validate_rbac_token.rb`, `tasks/check_legacy_compilers.rb`, `tasks/check_pe_master_rules.rb`, `tasks/get_peadm_config.rb`, `tasks/get_group_rules.rb`, `tasks/pe_ldap_config.rb`, `tasks/puppet_infra_upgrade.rb`, `tasks/backup_classification.rb`, `tasks/restore_classification.rb`, `tasks/code_manager_enabled.rb`, `tasks/code_sync_status.rb`, `tasks/node_group_unpin.rb`
- Impact: Each change to auth or TLS behavior needs to be made in many places, and the tasks are hard to test in isolation.
- Fix approach: Extract a shared helper (for example, under `files/`) that returns a configured `Net::HTTP` for PE service ports, and have tasks require it.

**Version-gate ladder in `pe_db_names`:**
- Issue: `functions/pe_db_names.pp` builds database names from a chain of `SemVerRange` checks (2023.8, 2025.0, 2025.3, 2025.6, 2025.11, 2026.0). Other version gates are scattered across plans with mixed comparators: `versioncmp` in `plans/convert.pp` (line 393) and `plans/restore.pp` (line 315), and `SemVerRange` in `plans/convert.pp` (line 135), `plans/upgrade.pp` (lines 190, 455), and `functions/assert_supported_pe_version.pp`.
- Impact: Adding a new PE line requires editing several unrelated files, and a missed gate fails only at runtime against a real cluster.
- Fix approach: Centralize PE-version feature flags in one function (similar to `peadm::supported_pe_versions`) and use it everywhere.

**Unresolved TODOs in the plan flow:**
- Issue: Several open TODOs mark known gaps: PE version is not read or validated in `plans/convert.pp` (line 34) and `plans/subplans/configure.pp` (line 56); `plans/modify_certificate.pp` (line 19) does not convert extension names to OIDs; `plans/restore.pp` (lines 245, 391) has no size heuristic for skipping steps; `plans/restore.pp` and `plans/subplans/install.pp` have TODOs about retry strategy; `tasks/puppet_runonce.sh` (line 13) only checks lock-file existence.
- Files: as listed.
- Impact: Operators can hit these gaps late in long-running plans.
- Fix approach: Track each TODO as a backlog item with a PE-version or behavior test.

**Stale or fragile internal PE paths:**
- Issue: `tasks/get_psql_version.rb` does `require '/opt/puppetlabs/puppet/cache/lib/pe_install/pe_postgresql_info.rb'`, which depends on an undocumented PE-internal cache layout. `tasks/pe_install.sh` sources `"$(dirname $0)/../../peadm/files/task_helper.sh"`, which assumes a specific module layout on disk. `plans/subplans/install.pp` (around lines 580-600) calls `/opt/puppetlabs/installer/bin/bolt` with a nested `plan run`.
- Files: `tasks/get_psql_version.rb`, `tasks/pe_install.sh`, `plans/subplans/install.pp`
- Impact: Any PE release that moves these files breaks the task with an unclear error.
- Fix approach: Check for the file's existence first and fail with a clear message. Pin expectations to the supported PE range in `data/pe_versions.yaml`.

## Known Bugs

**Installer drop-in left behind on early exit (extra-large installs):**
- Symptoms: After `pe_install.sh` runs with `install_extra_large=true`, `/etc/systemd/system/pe-puppetdb.service.d/10-shortcircuit.conf` (`TimeoutStartSec=1`, `Restart=no`) can remain on the node.
- Files: `tasks/pe_install.sh`
- Trigger: The script creates the drop-in near the top, but it exits early on "Failed to extract Puppet Enterprise tarball" and "Puppet Enterprise installer not found" before the cleanup block runs. Cleanup happens only after the installer returns.
- Workaround: Manually `rm` the drop-in and run `systemctl daemon-reload`.

**`begin_at_step` typos silently skip the entire plan:**
- Symptoms: If the `begin_at_step` value does not match any `peadm::plan_step` name, every step prints "SKIPPING" and the plan reports success.
- Files: `lib/puppet/functions/peadm/plan_step.rb` (lines 10-22)
- Trigger: Passing a misspelled or renamed step name.
- Workaround: Compare the passed value to the "# Plan Step:" output. Add validation that the value matches a known step.

**`puppetdb delete-reports` workaround is not restored on failure:**
- Symptoms: On disaster-recovery architectures upgrading from 2019.8+, the `delete-reports` CLI is replaced with a symlink to `true` and moved to `delete-reports.original`. The restore step runs only on the success path.
- Files: `plans/upgrade.pp` (lines 451-478)
- Trigger: The `puppet_infra_upgrade` task fails between the `mv`/`ln` and the restore.
- Workaround: On the replica, `mv .../delete-reports.original .../delete-reports`.

**Stale lock file blocks puppet runs:**
- Symptoms: `tasks/puppet_runonce.sh` waits up to the timeout for the agent lockfile to disappear, even when the lock is stale, then continues and may fail.
- Files: `tasks/puppet_runonce.sh` (lines 12-23)
- Trigger: Agent crashes or is killed mid-run and leaves the lockfile.
- Workaround: Remove the lockfile after confirming no `puppet agent` process is running.

**Replica removal does not happen on PE 2021.x:**
- Symptoms: `add_replica` leaves both the old and new replica registered.
- Files: `documentation/add_replica.md` (lines 85-89, documented as a known issue), `plans/add_replica.pp`
- Trigger: Running `add_replica` against PE 2021.x.
- Workaround: Remove the old replica manually. The docs say a future release will fix this.

**Possible truthiness bug for string `'false'` in legacy-compiler checks:**
- Symptoms: A legacy compiler is reported as classified as a primary node when the value is the string `'false'`.
- Files: `tasks/check_legacy_compilers.rb` (around line 40: `if node_classification['parameters']['pe_master']`). `tasks/check_pe_master_rules.rb` (lines 99-104) handles the same OID explicitly after the GJira-17 fix. The same string-vs-boolean hazard remains in the other check.
- Trigger: Classifier parameter stored as string `"false"` rather than boolean `false`. Not verified against a live PE classifier; confirm before fixing.

## Security Considerations

**TLS verification disabled for a PE service call:**
- Risk: `tasks/check_legacy_compilers.rb` sets `https.verify_mode = OpenSSL::SSL::VERIFY_NONE` for requests to `localhost:4433`, and presents the node's host cert and key.
- Files: `tasks/check_legacy_compilers.rb` (line 53)
- Current mitigation: Target is localhost only.
- Recommendations: Set `ca_file` to `Puppet.settings[:localcacert]` and use `VERIFY_PEER`, matching the other tasks. Use the shared helper from the TLS consolidation item above.

**Unverified tarball download and signature check:**
- Risk: `tasks/download.sh` fetches the PE installer over HTTP(S) with curl, then verifies a GPG signature only if `gpg` is present. If the signing key is not local, it is fetched on demand from `$PT_key_server`, which is trust-on-first-use. The function returns `EX_UNAVAILABLE` (69) when verification prerequisites are missing, and the caller must handle that code.
- Files: `tasks/download.sh` (lines 8-35, 40-60), `tasks/verify_tarball.sh` (checks structure only, not signature)
- Current mitigation: `tasks/verify_tarball.sh` detects truncated or corrupt tarballs (PE-42686).
- Recommendations: Require GPG verification for installer downloads, or fail when verification is unavailable. Pin the expected signing key fingerprint instead of fetching it on demand.

**Arbitrary file read as root:**
- Risk: `tasks/read_file.sh` runs as root under Bolt and returns the contents of any path. It also interpolates `$PT_path` into a Python string (`open('$PT_path','r')`), so a path containing a single quote breaks the command or injects code.
- Files: `tasks/read_file.sh` (main function)
- Current mitigation: Plans call it with known paths only.
- Recommendations: Pass the path through the environment (`os.environ['PT_path']`) and not inline. Restrict to an allowlist of paths if the task is exposed beyond peadm's own plans.

**Secret-bearing data in CI logs and inline shell:**
- Risk: Workflows pass `console_password=${{ secrets.CONSOLE_PASSWORD }}` inline in shell commands, and several workflows open ngrok and SSH sessions using `secrets.NGROK_AUTH_TOKEN` and `secrets.SSH_PASS` (`.github/workflows/test-add-replica.yaml` lines 37-42, `.github/workflows/test-backup-restore-migration.yaml` lines 32-37, and others).
- Files: `.github/workflows/test-install.yaml` (lines 41-42, 87), `.github/workflows/test-add-replica.yaml`, `.github/workflows/test-add-compiler.yaml`, `.github/workflows/test-backup-restore-migration.yaml`, `.github/workflows/test-migration.yaml`, `.github/workflows/test-add-replica-matrix.yaml`, `.github/workflows/test-fips-install-matrix.yaml`
- Current mitigation: `litmus_inventory.yaml` passwords are redacted with `sed` before log output.
- Recommendations: Pass secrets via `env:` and not inline. Restrict the `ssh-debugging` input to trusted actors.

**Unpinned third-party and CI actions:**
- Risk: `luchihoratiu/debug-via-ssh@main` and 25 other workflow references use `@main`, so their content can change without review. Several reusable workflows come from `puppetlabs/cat-github-actions` at `@main`.
- Files: `.github/workflows/test-add-replica.yaml` (line 39), `.github/workflows/test-add-compiler.yaml` (line 39), `.github/workflows/test-backup-restore-migration.yaml` (line 34), `.github/workflows/ci.yml` (lines 88-153)
- Current mitigation: None in repo.
- Recommendations: Pin to commit SHAs.

**Example and test credentials committed in plain text:**
- Risk: The literal `"puppetLabs123!"` is used as `console_password` in example and test parameter files. Users who copy them keep a known admin password.
- Files: `examples/provision/minimal.json`, `examples/provision/extra-large-ha.json`, `spec/docker/standard-ha/params.json`, `spec/docker/large-ha/params.json`, `spec/docker/large/params.json`, `spec/docker/extra-large/params.json`, `spec/docker/extra-large-ha/params.json`
- Current mitigation: These files are described as examples or test fixtures.
- Recommendations: Replace with placeholder values such as `"CHANGE_ME"` and document the requirement to supply a real value.

## Performance Bottlenecks

**Fixed-cost waits on every install:**
- Problem: The `ca_storage_import` probe in the install flow restarts `pe-puppetserver`, runs the Puppet agent, and polls readiness for up to about 145 seconds on every install, including ones already migrated. The code comments accept this cost.
- Files: `plans/subplans/install.pp` (around lines 570-600)
- Cause: The step runs unconditionally to avoid relying on a probe result.
- Improvement path: Gate on a cheap check (for example, `pe-ca` schema presence) before running the expensive path.

**Long serial retry loops:**
- Problem: Several retry loops sleep 15 seconds between attempts, with up to 10 attempts for the RBAC token. Each loop serializes on a single primary.
- Files: `plans/subplans/install.pp` (lines 448-487, 10 attempts), `plans/restore.pp` (lines 403-428, 5 attempts at 15s), `plans/add_replica.pp` (lines 142-218), `plans/subplans/configure.pp` (lines 135-156), `plans/subplans/component_install.pp` (lines 50-64), `tasks/wait_until_service_ready.sh` (20 attempts at 3s)
- Cause: Retries are used for warm-up races (PE-44867, PE-46689) rather than readiness checks.
- Improvement path: Replace fixed sleeps with readiness polling against the specific service endpoint.

**Installer tarball deleted before install:**
- Problem: `tasks/pe_install.sh` runs `rm -f "$PT_tarball"` after extraction. If the install then fails, the full PE tarball (multiple GB) must be downloaded again.
- Files: `tasks/pe_install.sh`
- Cause: Disk space management during install.
- Improvement path: Keep the tarball until the installer exits 0, or make deletion optional.

**Sequential `copy_file` calls:**
- Problem: `plans/subplans/configure.pp` and `plans/add_replica.pp` call `peadm::util::copy_file` once per path, and each call does a `read_file` on the primary followed by `mkdir_p_file` on the targets.
- Files: `plans/subplans/configure.pp` (lines 78-100), `plans/add_replica.pp` (lines ~101-115), `plans/util/copy_file.pp`
- Cause: Each file is copied in its own plan call.
- Improvement path: Read all sources in one `run_task` and upload in one batch.

## Fragile Areas

**Restore flow (SQL executed as the database owner):**
- Files: `plans/restore.pp` (lines ~260-320, `DROP SCHEMA public CASCADE` and `CREATE SCHEMA public` run through `su - pe-postgres`; `pg_database_owner` gated on PostgreSQL 14+, and `pg_restore` at lines 184 and 341)
- Why fragile: Hand-built shell SQL with nested quoting, version-gated behavior (PE-44867, PE-47558), and destructive schema drops. Changes in PE's PostgreSQL role model have already required fixes.
- Safe modification: Test against all supported PostgreSQL versions in `spec/acceptance` before changing the SQL. Keep the version gate and the explanatory comments in sync.
- Test coverage: `spec/plans/restore_spec.rb` (543 lines) checks plan logic. The SQL is not executed in unit tests.

**Install retries and readiness race handling:**
- Files: `plans/subplans/install.pp`, `plans/add_replica.pp`, `plans/subplans/configure.pp`, `plans/restore.pp`
- Why fragile: Each retry loop embeds its own error sanitizing (`peadm::sanitize_log_text`), its own permanent-vs-transient classification (`peadm/rbac-auth-failure` kind must be kept in sync between `tasks/rbac_token.rb` and `plans/restore.pp`/`plans/subplans/install.pp`, a string literal per the comment in `tasks/rbac_token.rb`), and its own fixed sleep.
- Safe modification: Change the error kind string in all three places together. Prefer adding a shared plan function over duplicating the loop.
- Test coverage: `spec/unit/task/rbac_token_spec.rb` covers the task. Plan-level retry behavior is only partially covered in `spec/plans/subplans/install_spec.rb`.

**Upgrade plan and legacy compilers:**
- Files: `plans/upgrade.pp` (544 lines), `plans/convert.pp` (503 lines), `plans/subplans/install.pp` (645 lines)
- Why fragile: Large plans with many `# lint:ignore` markers (about 52 suppressions across `plans`, `functions`, `manifests`, and `types`, in about 21 files) and many version-specific branches. Behavior depends on classifier state and PuppetDB extension values.
- Safe modification: Extract each version-gated branch into a named subplan, and add a spec for each branch.
- Test coverage: `spec/plans/upgrade_spec.rb` (661 lines) includes a TODO at line 618 noting that a file write is not verified.

**Supported PE range boundary:**
- Files: `data/pe_versions.yaml` (`newest: '2026.0'`), `functions/assert_supported_pe_version.pp` (line 26: `SemVerRange(">= ${oldest} <= ${newest}")`)
- Why fragile: The comment says `2026.0` means `2026.0.x`, but `<= 2026.0` in `SemVerRange` may be interpreted as `<= 2026.0.0`. The spec only checks `2035.0.0` as unsupported and `2026.0` as the range label, not `2026.0.1`. Also, `newest` must be bumped manually for each PE line, and it is currently `2026.0`, which should be checked against the current PE release line.
- Safe modification: Add a spec with `2026.0.1` and `2026.0.99` as supported, and a spec with `2026.1.0` as unsupported unless `permit_unsafe_versions=true`.

**Plan step resume (`begin_at_step`):**
- Files: `lib/puppet/functions/peadm/plan_step.rb`
- Why fragile: Resume works by skipping every step until the named one, with no validation. See Known Bugs.
- Safe modification: Collect known step names and fail when `begin_at_step` is not in the set.

## Scaling Limits

**Single primary as serialization point:**
- Current capacity: All orchestrated operations (`run_task`, `run_command`) for install, upgrade, and restore run from one Bolt controller against the primary, one plan at a time.
- Limit: Each step's wait loops (see Performance) add to total runtime per node. Large topologies (extra-large HA) stack these waits.
- Scaling path: Run independent per-node tasks in `parallelize` where dependencies allow. `plans/add_replica.pp` already does this for `copy_file`.

**PE version support list:**
- Current capacity: Supported PE range is `2019.7` through `2026.0` (`data/pe_versions.yaml`).
- Limit: Each new PE line needs a peadm release, a bump in `data/pe_versions.yaml`, and new version gates (`functions/pe_db_names.pp`, plans listed above).
- Scaling path: Centralize version gates as described under Tech Debt.

## Dependencies at Risk

**GitLab CI runs on end-of-life Ruby and Puppet:**
- Risk: `.gitlab-ci.yml` runs on `ruby:2.5.7` with `PUPPET_GEM_VERSION: '~> 6'` and `ruby:2.7.2` with `'~> 7'`. `.ruby-version` is `3.1.0`. `Gemfile` supports Puppet 9 and Ruby 4 only through an experimental job in `.github/workflows/ci.yml` that uses a private gem source.
- Impact: The GitLab pipeline may no longer reflect what ships, and Ruby 2.5 images are no longer maintained.
- Migration plan: Retire `.gitlab-ci.yml` if GitHub Actions is the source of truth, or update the image and Puppet versions to match `Gemfile`.

**Private `puppetcore` gem source for Puppet 9:**
- Risk: The experimental Puppet 9 / Ruby 4 CI job depends on `https://rubygems-puppetcore.puppet.com` and `PUPPET_FORGE_TOKEN`. Only a documented internal process (Confluence) explains how to consume it.
- Impact: Builds break when the token or source is unavailable.
- Migration plan: Document the access process in the repo, or gate the job so it does not block release.

**PE-internal Ruby library requires:**
- Risk: `tasks/get_psql_version.rb` requires PE's private `pe_install/pe_postgresql_info.rb` by absolute path.
- Impact: PE upgrades that move or rename this file break the task.
- Migration plan: Query the PostgreSQL version through `psql` or a stable PE API.
